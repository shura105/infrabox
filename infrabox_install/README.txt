Скрипти пронумеровані за порядком виконання (0 → 5). Номер показує вашу
позицію в стеку процесів. Допоміжні інструменти — без номера.

Вимоги на admin-машині: bash, ssh, python3.
Цільові хости: core/adm — Linux; ui/arch — будь-яка ОС з Docker.

ФІЛОСОФІЯ: скрипти — інструменти адміна. Вони дають дані й виконують рішення,
але не приймають їх за вас. Топологію, адреси, внутрішні зв'язки та проблеми
продумує і вирішує адмін. Авто-discovery немає.

Модель: кожен ОБ'ЄКТ (дім/дача/офіс) — автономна повна система; внутрішні
зв'язки — локальна мережа об'єкта. Між об'єктами — WireGuard на MikroTik
(мережевий рівень, ПОЗА цими скриптами).

  СТЕК — ПОРЯДОК ВИКОНАННЯ
━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━

  0_probe.sh      ПЕРШИЙ крок. Тонкий автономний збирач ДАНИХ про вузол:
                  hardware, os, мережа, тип носія, docker, wireguard, порти
                  → host-report-<hostname>.json. Ролей не питає.
                  Запуск НА ЦІЛЬОВОМУ ХОСТІ, нічого не змінює. Працює навіть за
                  обмеженого доступу.

  1_prepare.sh    Формує topology.yml — ДЖЕРЕЛО ІСТИНИ — зі звітів 0_probe.
                  Факти (arch/os) і розподіл ролей беруться зі звітів; адмін
                  додає рішення: SSH-користувач/ключ, deploy_dir, repo/branch/JWT.
                  Запуск на ADMIN-МАШИНІ.

  2_host-prep.sh  Підготовка хоста: Docker, мережа infrabox-net, SSL,
                  logrotate, tmpfs для логів.
                  Запуск НА ЦІЛЬОВОМУ ХОСТІ (від sudo-користувача).

  3_deploy.sh     Розгортання підсистем на їхні вузли (за topology.yml).
                  git clone/pull + docker compose up. Мультихост.
                  Запуск на ADMIN-МАШИНІ (по SSH).

  4_status.sh     Стан системи по всіх вузлах: контейнери, ресурси, git.
                  Запуск на ADMIN-МАШИНІ (по SSH).

  5_uninstall.sh  Видалення з вузлів: зупинка / інтерактивне / повне.
                  Запуск на ADMIN-МАШИНІ (по SSH).

  ── Допоміжні (без номера) ──
  gen-ssh-key.sh  Генерація SSH-ключа для доступу до вузлів.
  _topo.py        Парсер topology.yml (спільний для 3/4/5). Не запускати вручну.

  ДЖЕРЕЛО ІСТИНИ: topology.yml
━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━

Один файл — джерело правди для всього стеку. Життєвий цикл:

  0_probe    → ЗБИРАЄ факти про вузол (host-report-<host>.json на кожному вузлі)
  1_prepare  → БУДУЄ topology.yml зі звітів + рішень адміна
  3/4/5      → ЧИТАЮТЬ (через _topo.py)

Природний порядок — спершу факти, потім план. Поділ відповідальності:
  • 0_probe   = ФАКТИ хоста (архітектура, ОС, тип носія, готовність) — без ролей
  • 1_prepare = РІШЕННЯ адміна: розподіл ролей (з підказкою придатності за
    фактами) + SSH/deploy_dir/repo/branch — і збірка плану

Секції topology.yml:
  system:         назва, repo, branch, timezone
  nodes:          вузли: host, user, ssh_key, deploy_dir, arch, os, role
  subsystems:     підсистеми: node (← на якому вузлі), workdir, containers, ports
  deploy_order:   порядок розгортання (core першим)
  undeploy_order: порядок зупинки (core останнім)
  data:           volumes і bind-директорії (для backup і uninstall)

УВАГА: містить JWT_SECRET і шляхи SSH-ключів — не комітити в публічний репо.

Кілька середовищ: 1_prepare пише topology.yml; для інших — --topology:
  bash 3_deploy.sh --topology prod.yml
  bash 4_status.sh --topology staging.yml

  ПЕРША УСТАНОВКА — ПОРЯДОК ДІЙ
━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━

Перед стеком (за потреби): SSH-ключ для доступу до вузлів
  -- на ADMIN-МАШИНІ --
  bash gen-ssh-key.sh homeServ2
  → створить ~/.ssh/infrabox_homeServ2, виведе як скопіювати .pub на хост.

Крок 0. Зібрати дані про кожен хост
  -- НА КОЖНОМУ ЦІЛЬОВОМУ ХОСТІ --
  bash 0_probe.sh                          (локально)
  або:  ssh user@host 'bash -s -- --json' < 0_probe.sh > host-report-<host>.json

  → Зведення фактів + host-report-<hostname>.json. Ролей не питає.
  → Складіть звіти всіх вузлів в одну теку на admin-машині (scp / флешка).

Крок 1. Закласти джерело істини
  -- на ADMIN-МАШИНІ (у теці зі звітами) --
  bash 1_prepare.sh                        (без ключів — сам збере host-report*.json)

  → Зі звітів: вузли з фактами (arch/os). Розподіл ролей — ти обираєш,
    скрипт підказує придатність (core/adm лише Linux; arch краще SSD).
  → Адмін додає: SSH-користувач/ключ, deploy_dir, repo/branch/JWT, SSL.
  → Результат: topology.yml.

Крок 2. Підготувати кожен хост
  -- НА КОЖНОМУ ЦІЛЬОВОМУ ХОСТІ --
  bash 2_host-prep.sh                      (без ключів — питає deploy_dir, SSL у процесі)

  → Перевіряє/готує: Docker, infrabox-net, SSL, (Linux) docker-група, logrotate, tmpfs.
  → Що не може встановити сам (напр. Docker Desktop/Colima на macOS) — видає
    ЗАДАЧУ адміну з описом і виходить (код 2), а не падає.
  → Після: можливо потрібен newgrp docker або re-login (Linux).

Крок 3. Розгорнути систему
  -- на ADMIN-МАШИНІ --
  bash 3_deploy.sh

  → Клонує репо на кожен вузол (repo/branch з topology.yml).
  → docker compose up для підсистем кожного вузла у порядку deploy_order.

  Окремі підсистеми / перевірка плану:
  bash 3_deploy.sh core
  bash 3_deploy.sh --dry-run

Крок 4. Перевірити стан
  bash 4_status.sh

━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━

Збирає ФАКТИ про вузол — ролей не питає (їх призначає адмін у 1_prepare). Блоки:
  hardware, os, network (primary_iface/ip, mdns_name)
  storage   — тип носія (ssd/hdd/sd)
  wireguard — kernel, wg-tools, UDP 51820, ip_forward
  time      — NTP-синхронізація (для desync_guard)
  readiness — docker running, інтернет, mDNS, firewall, пакетний менеджер

Придатність 1_prepare підказує на основі цих фактів:
  core/adm — лише Linux (платформа зі звіту)
  arch     — носій SSD/HDD краще за SD (тип носія зі звіту)
  ui       — будь-де

wg-готовність — лише дані; тунелі між об'єктами тримає MikroTik, не вузли.

  ПІДТРИМУВАНІ ПЛАТФОРМИ (ЦІЛЬОВИЙ ХОСТ)
━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━

  Платформа залежить від підсистеми (Docker дає незалежність для мережевих):

    core — Linux (жорстко)   selfdiag міряє метрики РЕАЛЬНОГО хоста (/proc,/sys);
                             на Docker Desktop це була б ВМ, не машина
    adm  — Linux (жорстко)   pid:host + керування хостом (reboot/shutdown)
    ui   — будь-яка з Docker  web+backend — мережеві контейнери
    arch — будь-яка з Docker  writer+backend+arch-ui — мережеві + диск

  1_prepare підказує придатність за фактами probe: core/adm на не-Linux позначає
  непридатним; ui/arch — придатні скрізь.
  Операторська машина (Mac/Linux) може нести ui (+ arch). core/adm — на Linux-вузлах
  об'єкта, на одному або різних. Вузли об'єкта спілкуються локальною мережею;
  міжоб'єктний зв'язок (WireGuard на MikroTik) — поза цими скриптами.

  Перевірено:  Armbian (Debian 12) / ARMv7 — Banana Pi M2 Ultra (root на SATA SSD)
               macOS 15 / x86_64 — Mac mini (probe: ui/arch ok, core fail)
  Сумісно:     Debian 11/12, Ubuntu 22/24, DietPi, Armbian (core/adm);
               будь-яка ОС з Docker для ui/arch. Windows — планується (WSL/Git Bash).
  Мінімум RAM: 256 MB (512 MB рекомендовано для arch)
  SD-карта:    логи і архів у RAM (tmpfs); для arch краще SSD/HDD-вузол

Винесення архіватора на окремий вузол (SSD-машина):
  1. 0_probe на A і на B → host-report-A.json, host-report-B.json (в одну теку)
     → звіт B покаже носій SSD/HDD (1_prepare підкаже придатність arch)
  2. bash 1_prepare.sh  (сам збере звіти) → познач: core/ui/adm на A, arch на B
  3. bash 2_host-prep.sh на A і B
  4. bash 3_deploy.sh

Деплой нової версії коду:
  bash 3_deploy.sh

Проблема з підсистемою:
  bash 4_status.sh            → знайти проблемний контейнер/вузол
  bash 3_deploy.sh core       → перерозгорнути тільки core

Тимчасова зупинка:
  bash 5_uninstall.sh --keep-data --force
  ... обслуговування ...
  bash 3_deploy.sh
