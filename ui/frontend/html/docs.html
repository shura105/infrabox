Огляд системи

Infrabox — домашня SCADA-система для моніторингу та управління інженерними підсистемами об'єкта. Розгорнута на одноплатнику (наприклад, Banana Pi M2 Berry) у вигляді набору Docker-контейнерів. Дані збираються через MQTT, обробляються Core-сервісом, зберігаються в Redis та архівуються на диск, а відображаються на налаштовуваних екранах у реальному часі через WebSocket.

Основні можливості

  • Відображення значень параметрів у реальному часі через WebSocket із пуш-оновленнями (без поллінгу)
  • Налаштовувані SCADA-екрани з довільним розташуванням елементів — побудовані візуальним конструктором
  • Три типи екранів: PC, Render (пряма передача зображення), Mobile
  • Авто-визначення мобільного клієнта і вибір відповідного екрана при першому завантаженні
  • Підтримка кількох фізичних пристроїв відображення (D1, D2…) у межах одного типу
  • Класифікація якості сигналу (GOOD / WARN / ALARM / UNCERT / INIT / NODATA) із кольоровою індикацією
  • Архівування всіх параметрів зі змінною/інтервальною стратегією, побудова трендів
  • Самодіагностика хосту (cpu, mem, disk, мережа) і моніторинг heartbeat кожного контейнера
  • Симулятор для тестування без реального обладнання
  • Рольова система доступу з гранулярними правами на рівні сторінок та об'єктів
  • Адаптивний дизайн UI під мобільні пристрої та планшети
  • HTTPS із валідним сертифікатом (TLS termination в nginx, mkcert для локальної мережі)

Що цей документ описує

Цей документ — повний посібник для оператора та адміністратора системи. Він описує архітектуру, маршрути, концепції точок і сокетів, типи екранів, конструктор, архівацію, контроль доступу та налаштування TLS. Якщо ви новий користувач — починайте з Архітектури та Потоку даних.

Архітектура

Система розгорнута у Docker-контейнерах в одній мережі infrabox-net. Кожен сервіс — окрема відповідальність, обмін через MQTT (для значень) та Redis (для стану). Всі компоненти періодично записують heartbeat:<name> у Redis з TTL 25с — так система знає, що сервіс живий.

Зовнішній шар (HTTPS)

🌐 infrabox-web (nginx)
:80 → :443 · HTTPS-точка входу

Єдина точка входу. Роздає статику HTML/JS, проксіює /api/, /auth/, /adm/api/, /arch/api/, WebSocket /ws. TLS termination — серт монтується з ui/frontend/ssl/. HTTP перенаправляється на HTTPS.

Логіка та авторизація

⚙ infrabox-backend
:8090 · FastAPI + uvicorn

REST API для перегляду екранів та проекту. WebSocket-стрім даних з batch-оновленнями (200мс) через Redis Pub/Sub. Керує симулятором через Docker-сокет.

🔑 infrabox-auth
:8095 · FastAPI

Логін / реєстрація / зміна паролю. Видає JWT-токени з payload: username, role, display_name, permissions, exp.

🛠 infrabox-adm
:8099 · /adm/api/

Адмін-API: керування об'єктами/системами/вузлами/точками, конфіги, перегляд Redis, керування Docker-підсистемами (старт/стоп/рестарт/ребілд) через SSH.

Дані та шина

🗄 infrabox-redis
:6379

Поточні значення (point:NNN hash), користувачі (users:*), heartbeat (heartbeat:NAME, TTL=25с), системні ключі (system:*). Шина повідомлень: bus:data, bus:event, bus:clock через Pub/Sub.

🦟 infrabox-mosquitto-real
:1883 · MQTT broker

Приймає дані від реального обладнання. Топіки {object}/{system}/{pointname}/{id}.

🦟 infrabox-mosquitto-sim
:1884 · MQTT broker

Окремий брокер для симульованих даних. Дозволяє розділити трафік від реального обладнання.

Обробка та джерела даних

🧠 infrabox-core
Python · читає MQTT

Підписується на MQTT, валідує топіки, застосовує deadband, класифікує якість, пише в Redis (point:NNN) і публікує bus:data/bus:event. Системний tick = 1с.

🤖 infrabox-simulator
→ mosquitto-sim

Генерує тестові значення для всіх не-діагностичних точок з ID ≥ 100. Випадкові спайки (warn/alarm) кожні ~15с.

🩺 infrabox-selfdiagnostic
→ mosquitto-sim

Збирає метрики хоста (cpu, mem, disk, net) через psutil і публікує як діагностичні точки сокета selfDiag.

Архівація та її UI

📦 infrabox-arch
:8100 · архіватор

Слухає bus:data/bus:event, пише ndjson-файли у томи (volumes). Стратегія: deadband + інтервал. Окремі стріми values, events, selfdiag.

🌐 infrabox-arch-backend
:8101 · FastAPI

Проксі-API для UI архіватора. Читає томи з infrabox-arch, виконує downsampling для побудови графіків.

📊 infrabox-arch-ui
nginx · /arch/

Веб-інтерфейс архіватора. Список параметрів, графіки (Chart.js), експорт CSV.

Топологія: усі контейнери в єдиній Docker-мережі infrabox-net. Зовні доступний лише infrabox-web (порт 443). Решта спілкується через імена контейнерів та DNS Docker.

Перегляд екранів

Головна сторінка (/) відображає SCADA-екрани у реальному часі. При завантаженні автоматично відкривається перший екран, що відповідає обраному пристрою відображення та типу клієнта (мобільний/десктоп).

Авто-вибір стартового екрана

Логіка при першому завантаженні:

  1. Визначається тип клієнта: matchMedia('(max-width: 768px)') → mobile / desktop
  2. Серед екранів проекту з відповідним screenType і поточним deviceType вибирається той, що має найменший screenNum
  3. Якщо файл екрана не знайдено на диску — fallback на _rootForDevice(dt) (просто найменший screenNum для пристрою), потім на 'root'
Якщо в проекті є записи M1/M2 але немає data/screens/M1/screen.json — мобільний клієнт автоматично побачить PC-екран. Створюй мобільні екрани в конструкторі.

Навігація між екранами

  • Кнопки Навігація та картки Підсистема переходять на інший екран того ж типу та пристрою
  • Кнопка ← в хедері повертає на попередній екран (стек навігації history)
  • Назва поточного екрану відображається по центру хедера
  • Переходи між екранами різних типів або різних пристроїв заблоковані (захищає від випадкового виходу з мобільного простору на PC)

Статус авторизації в хедері

Іконка користувача показує стан логіну:

  • Якщо JWT в localStorage валідний (exp > now) — показується ім'я / роль користувача, у меню — "Вийти"
  • Якщо токен прострочений або зіпсований — він автоматично видаляється, відображається "operator", у меню — "Увійти"
  • Кнопка "Увійти" → /login

Статус з'єднання WebSocket

Нижній рядок (футер) показує стан:

  • ● Live — дані надходять у реальному часі
  • ● Підключення… — встановлюється
  • ● Помилка — з'єднання перервано, виконується повторне підключення з exponential backoff (1s, 2s, 4s… до 30с)

Поряд показується час останнього batch-апдейту і розміри полотна {width}×{height}.

Адаптивність

На вузьких екранах (≤ 768px):

  • Логотип згортається до іконки ⬡
  • Розділювачі ховаються
  • Ім'я користувача ховається (залишається 👤)
  • Дата в годиннику ховається (залишається час)
  • Кнопка "☰ Меню" → "☰"
  • Падінги і відступи скорочуються — більше місця для канваса

Пристрої відображення

Кожен екран у системі прив'язаний до конкретного пристрою відображення — числового параметра D1, D2, D3… Це дозволяє мати окремі набори екранів для різних фізичних дисплеїв одного типу.

Вибір пристрою

У меню ☰ Меню → Пристрій відображення відображається список пристроїв, доступних для поточного типу екрана. Вибір зберігається в localStorage.

Фільтрація: меню показує лише ті номери пристроїв, для яких є екрани того ж типу що й поточний (PC/Render/Mobile). Якщо для PC немає екранів D2 — D2 в меню не з'явиться.

Початковий екран

При завантаженні або зміні пристрою система завантажує екран з найменшим screenNum серед екранів обраного пристрою.

Конструктор — огляд

Сторінка /constructor — лендінг з вибором напрямку конструювання:

  • Структура і екрани (/constructor-screens) — побудова структури екранів та редагування їх елементів
  • Обладнання (/constructor-equipment) — конфігурація обладнання (в розробці)

Доступний тільки авторизованим адміністраторам.

Режими роботи конструктора екранів

  • Структура — управління переліком екранів: створення, видалення, розташування на канвасі або в таблиці
  • Елементи — редагування вмісту конкретного екрана (подвійний клік на екрані в режимі структури)
Зберігання: зміни зберігаються кнопкою 💾 Зберегти. Автозбереження відсутнє.

Типи та нумерація екранів

Кожен екран належить до одного з трьох типів:

P — PC R — Render M — Mobile
ТипПрефіксПризначення
PCPВеб-інтерфейс для комп'ютерних браузерів
RenderRПряма передача зображення на дисплей (bitmap по мережі, тільки дельти)
MobileMКомпактний інтерфейс для мобільних пристроїв

Ідентифікатор екрана

ID генерується автоматично при створенні: P1, P2, R1, R12, M1…

Окрім ID кожен екран має два числових параметри:

  • Номер екрана (screenNum) — логічний номер, визначає рядок у таблиці структури. Редагується у властивостях екрана.
  • Пристрій відображення (deviceType) — номер фізичного дисплея (D1, D2…). Встановлюється при створенні, редагується у властивостях.
Навігація: переходи між екранами дозволені лише в рамках одного типу (PC↔PC, R↔R…) і одного пристрою (D1↔D1…).

Структура проекту

Графічний вигляд

Кожен екран відображається як картка з назвою, ID, типом (P/R/M) і номером пристрою. Картки можна вільно перетягувати по канвасу. Декоративні елементи (групи, підписи, стрілки) додаються з лівої палітри drag&drop.

Табличний вигляд

Кнопка ⊞ Таблиця в тулбарі перемикає на матричне представлення:

  • Рядки — номери екранів (screenNum)
  • Стовпці — тип × пристрій (PC D1, PC D2, Render D1…)
  • Клік на комірці — вибирає екран у панелі властивостей
  • Подвійний клік — відкриває редактор елементів

Файлова структура

Дані екранів зберігаються плоско: data/screens/{ID}/screen.json. Структура проекту (список екранів, позиції) — у data/project.json.

Типи елементів

Елементи додаються перетяганням з палітри на полотно. Розмір і позиція задаються у відсотках від розмірів екрана.

Редагування кінцевих точок лінії та стрілки

При виборі елемента типу Лінія або Стрілка з'являються два маркери — ● синій (початок) та ● жовтий (кінець). Перетягніть маркер мишкою для зміни позиції точки всередині bounding box елемента.

Групування елементів

Елемент Група (group_box) охоплює розташовані всередині елементи. При переміщенні групи всі вкладені елементи рухаються разом. Z-index груп нижчий за звичайні елементи, щоб внутрішні елементи залишались інтерактивними.

Параметри (точки)

Кожен параметр системи — це точка з унікальним числовим id. Конфігурація точок зберігається у файлі core/service/config/points.json (масив об'єктів). Поточне значення — у Redis як хеш point:NNN.

Архівування discrete

Принципово відрізняється від analog: тільки за зміною. Без deadband, без інтервального семплінгу, без gap-writer (стабільний стан під час тиші — нормально). Кожен перехід 0→1 або 1→0 записується одним рядком у values.ndjson.

Відображення на канвасі

  • Значення точки — показує label_0/label_1, якщо вони задані; інакше сирі 0/1. Колір з quality.
  • Індикатор — колір з quality. Для severity=none завжди GOOD-колір.
  • Підсистема (картка) — колір рамки з quality. Працює.
  • Манометр, Рівень — не релевантні для discrete (рекомендується не використовувати).

Поля для diagnostic

ПолеОпис

Чому два набори полів? Аналогові точки прив'язані до фізичних об'єктів і підсистем користувача (home/heating). Діагностичні — до інфраструктурних сокетів (selfDiag, Core…). Сокетна абстракція дозволяє додавати нові апаратні чи програмні джерела даних без зміни схеми точок. Деталі — у секції Сокети та діагностика.

MQTT-топік для значення

Симулятор та selfdiag публікують значення на брокер MQTT за схемою:

{object|OBJECT}/{system|socket}/{pointname}/{id} → JSON {"id":N,"value":X,"ts":T}

Для діагностичних точок object заміщується env-змінною OBJECT (за замовчанням home), system заміщується socket.

Як працюють пороги якості

Core при обробці кожного значення класифікує його:

  • v < min або v > max → UNCERT (поза фізичним діапазоном)
  • v < alarm_min або v > alarm_max → ALARM
  • v < warn_min або v > warn_max → WARN
  • Інакше → GOOD

Перехід ALARM/WARN → GOOD відбувається з recovery_time_ms (за замовчанням 3 секунди).

Сокети та діагностика

Сокет — точка приєднання інфраструктурного джерела даних до вузла системи. Сокети відрізняють діагностичні точки (метрики хосту, стан сервісів) від користувацьких точок з обладнання. Конфігурація — у файлі core/service/config/sockets.json.

Структура sockets.json

Файл — масив вузлів, кожен містить hardware та software сокети:

[ { "drop": "homeServ-1", "hardware": [{"id":"selfDiag","name":"Selfdiagnostic","params":["cpu_load","mem_used","disk_space","net_rx","net_tx"]}], "software": [{"id":"Core","name":"infrabox-core","type":"heartbeat","params":["heartbeat"]}, …] } ]

Hardware-сокет selfDiag

Один сокет з 5-ма параметрами. Сервіс infrabox-selfdiagnostic:

  • Періодично опитує psutil на хості (/host/proc, /host/root змонтовані)
  • Публікує MQTT топік home/selfDiag/{pointname}/{id} з JSON-значенням
  • Параметри: cpu_load (%), mem_used (%), disk_space (%), net_rx / net_tx (Mbps)
  • Кожна метрика — окрема точка з type: "diagnostic", socket: "selfDiag", param: "<metric>"

Software-сокети (heartbeat)

Кожен контейнер системи має свій software-сокет. Принцип:

  1. Контейнер у фоновому потоці пише heartbeat:{container-name} з TTL=25с (наприклад, heartbeat:infrabox-core)
  2. Якщо контейнер живий — ключ оновлюється кожні 5 секунд, TTL зберігається
  3. Якщо контейнер впав — ключ зникає за 25с
  4. Core читає TTL ключа і перетворює його у бінарну точку: TTL > 0 → value=1, quality=GOOD; інакше value=0, quality=ALARM
  5. Така точка має socket: "Core" (або іншу назву сервісу), param: "heartbeat"
Контейнери без Python (redis, mosquitto, nginx, portainer) не можуть писати власний heartbeat. Для них heartbeat генерує proxy-механізм адмін-сервісу — він раз на 5с перевіряє стан Docker-контейнера і пише ключ за нього.

Якість сигналу

Поле quality точки впливає на колір елементів на екрані.

GOOD — норма
WARN — попередження
ALARM — аварія (миготить)
UNCERT — невизначено
INIT — ініціалізація
NODATA — немає даних

Елементи Значення точки, Індикатор, Рівень, Манометр та Підсистема автоматично змінюють колір залежно від якості.

Симулятор

Контейнер infrabox-simulator генерує тестові значення і публікує через окремий брокер infrabox-mosquitto-sim. Дозволяє тестувати без реального обладнання.

Які точки симулюються

Тільки не-діагностичні точки з id ≥ 100. Діагностичні (selfDiag, heartbeat) ігноруються — їх генерує infrabox-selfdiagnostic і core напряму.

Аналогові — безперервна емуляція

Для кожної аналогової/розрахункової точки симулятор тримає поточне значення і кожну секунду:

  • Зазвичай — невелике дрейфування навколо середнього між warn_min і warn_max (drift = 2% від цього діапазону)
  • Раз на ~15 секунд — спайк на 5 секунд:
    • З вірогідністю 60% — ALARM-зона (поза alarm_min/alarm_max)
    • 40% — WARN-зона (між warn і alarm межами)

Дискретні — за зміною стану

Для кожного дискретного параметра симулятор обирає сценарій залежно від severity:

  • severity=none — toggle-режим: випадкове перемикання 0↔1 кожні 30—120 секунд (мотор on/off, насос). Початкове значення випадкове.
  • severity=warn|alarm — event-режим: переважно normal_value, кожні 60—180с тригериться "подія" (перехід у протилежний стан) на 5—30 секунд, потім повертається до normal_value.

Дискретні значення публікуються лише на переходах (edge-triggered) з прапором retain=True у MQTT — щоб core, що підключився пізніше, одразу отримав актуальний стан з брокера.

Додатково раз на 3—10 хвилин симулятор інжектить glitch — випадкове значення поза 0/1 (-1, 2, 3, 9) на один тік. Це емулює помилки шини / протоколу і дозволяє перевірити що core правильно класифікує такі значення як UNCERT. Наступним тіком значення повертається до коректного.

Через edge-trigger логіку для дискретних точок core пропускає десинк-перевірку (немає сенсу позначати NODATA у стабільному стані). Коректний спосіб виявити "мертвий" датчик — окремий keepalive-сигнал, не реалізовано наразі.

{object}/{system}/{pointname}/{id} — те саме формування, що і реальне обладнання.

Увімкнення / вимкнення

Керується зі сторінки Адмін → Застосунки → Симулятор: кнопки Запустити / Зупинити (контейнер ставиться на паузу).

Перемикання джерела даних (sim ↔ real)

Core підписується лише на один MQTT-брокер — залежно від поля data_source у секції bootstrap файлу core/service/config/sys_params.json:

  • "sim" — core підключається до infrabox-mosquitto-sim; дані надходять від симулятора (тест без обладнання).
  • "real" — core підключається до infrabox-mosquitto-real; дані надходять від реального обладнання (пристроїв нижнього рівня).

Щоб перемкнути: змініть data_source у sys_params.json і перезапустіть контейнер infrabox-core (напр. docker restart infrabox-core або через Адмін → Композитор). Перевірити, до якого брокера підключився core, можна в логах: docker logs infrabox-core | grep "MQTT connected".

Важливо: sys_params.json — це JSON, він не допускає коментарів (// …). Якщо дописати коментар (напр. "data_source": "real" //sim/real), core не розпарсить конфіг і впаде в цикл рестарту — увесь збір даних зупиниться. Пишіть значення чисто: "data_source": "real".
Наслідок вибору: у режимі sim повідомлення реальних пристроїв, що йдуть у mosquitto-real, ігноруються (core їх не слухає), і навпаки. Тож для тесту реального пристрою нижнього рівня переконайтесь, що data_source = "real"; а для чистого тесту з симулятором тримайте "sim" і за потреби зупиняйте симулятор.

Архіватор

Архівна підсистема складається з трьох контейнерів: infrabox-arch (writer), infrabox-arch-backend (API) та infrabox-arch-ui (web). UI доступний за адресою /arch/.

Архів організовано по томах — окремих директоріях зі стартовою датою у форматі YYYY-MM-DD_HH-MM-SS. У кожному томі:

Gap-writer (заповнення тиші)

Якщо точка мовчить довше за max(interval × 3, 120) секунд, архіватор записує value: null. На графіку це відображається розривом — видно, коли реально не було даних.

Watchdog та resilience

  • Окремий тред слухає bus:clock від core — якщо тиша > 10 с, перепідключається до Redis
  • Rotation watchdog примусово ротує том, якщо умови виконуються але write() не викликався (нет нових даних)
  • Watcher на points.json — при зміні файлу points_meta перезавантажується (1 раз на хвилину)

UI можливості

  • Список усіх параметрів (з config_snap поточного тому), фільтри за Object/Drop, System/Socket, ID, пошук за назвою
  • Вибір до 4 параметрів одночасно для порівняльного тренду
  • Період — за датами або режим "Current" (поточний том)
  • Перемикач графік / таблиця
  • Зум по горизонталі (клавіші − +)
  • Експорт CSV, друк
  • Downsampling на бекенді (LTTB-подібний) до CHART_MAX_POINTS

Обмеження зберігання

На сторінці Адмін → Архіви можна змінити max_days — глибину зберігання. Старші тома видаляються автоматично.

Адміністрування

Сторінка /admin — тільки для адміністраторів. Складається з 7 вкладок:

Користувачі

Перелік облікових записів. Дозволяє створювати/видаляти користувачів, змінювати пароль, призначати роль (admin / operator / constructor) та display_name.

Права доступу

Матриця дозволів для не-адмін користувачів:

  • Сторінки — список slugs сторінок, до яких користувач має доступ (наприклад, dashboard). Якщо список порожній — всі дозволені сторінки
  • Об'єкти — список object-ів, які користувач бачить у Dashboard / на екранах (фільтрація /api/points)
Після зміни прав оператор має перелогінитись, щоб отримати оновлений JWT.

Система

Дві підвкладки:

  • Вузли — список фізичних серверів (drops). SSH-ключі для деплою. Стан кожного хоста.
  • Композитор — управління підсистемами Docker. Перелік сервісів, їхні шляхи, контейнери, кнопки для білду й деплою.

Застосунки

Огляд внутрішньої структури системи:

  • Структура бази даних — секція з hardware/software сокетами і поточними значеннями кожного параметра. Heartbeat-точки відображаються як одиничні записи зеленого/сірого кольору.
  • Симулятор — старт / стоп симулятора (з footnote про конфлікт з реальними даними).
  • Посилання 🔍 Redis → /redis-db для повного перегляду структури Redis.

Метадані

Дерево фізичної структури: об'єкти → вузли → системи + серверні підсистеми. Дозволяє створювати/редагувати/видаляти кожен рівень. При видаленні об'єкта/вузла/системи всі прив'язані до них точки автоматично видаляються (cascading delete).

Параметри

CRUD для точок (зчитує/пише points.json). Особливості UI:

  • Точки згруповані за типом: Підключені до сокетів (діагностичні), Аналогові, Дискретні, Розрахункові, Від зовнішніх систем
  • Розгортання/згортання групи кліком по заголовку
  • Сокетні точки мають окремі колонки: Вузол / Сокет замість Об'єкт / Система
  • Невалідні значення (вузол/сокет/об'єкт/система не існує в Метаданих) підсвічуються рожевим
  • Кнопка ↺ Застосувати зміни просить core перезавантажити points.json (вони підвантажуються автоматично кожну хвилину, але кнопка прискорює)
  • 💾 Резервувати — створює бекап усіх конфіг-файлів у config/backup/<timestamp>/

Архіви

Перегляд томів архіватора, список з розмірами, можливість примусово ротувати поточний том. Налаштування глибини збереження (max_days).

У розділі Права доступу адмін-панелі задається список сторінок (наприклад, dashboard), до яких має доступ конкретний оператор. Якщо список не заданий — оператор бачить всі дозволені сторінки.

Фільтрація об'єктів

Поле objects у правах — список об'єктів даних, які оператор може переглядати. API /api/points автоматично фільтрує точки для не-адміністраторів.

JWT-токен містить поточні права. При зміні прав оператору необхідно перезайти, щоб отримати оновлений токен.

TLS-сертифікат

Система працює виключно через HTTPS. Nginx (infrabox-web) виконує TLS termination на порту 443. HTTP-запити на порт 80 перенаправляються на HTTPS.

Поточний сертифікат

Серт і приватний ключ знаходяться у ui/frontend/ssl/infrabox.crt та infrabox.key на хості, монтуються у контейнер infrabox-web як /etc/nginx/ssl/ у режимі read-only. Файли не комітяться в git (виключені у .gitignore) — вони специфічні для кожного інсталяшу.

Генерація через mkcert (рекомендовано)

Для домашньої мережі найзручніше використовувати mkcert — інструмент, що створює локальний CA і підписує ним серти для будь-яких хостів/IP.

На Mac/Linux:

  1. Встанови: brew install mkcert nss (macOS) або sudo apt install mkcert (Debian/Ubuntu)
  2. Створи локальний CA: mkcert -install — додає CA в системний trust store (потрібно sudo)
  3. Згенеруй серт у директорії ui/frontend/ssl/:
    mkcert -cert-file infrabox.crt -key-file infrabox.key homeServ2.local homeServ2 localhost 127.0.0.1 192.168.1.105
  4. Скопіюй кореневий CA у проект для роздачі мобільним:
    cp "$(mkcert -CAROOT)/rootCA.pem" ui/frontend/ssl/
  5. Перебудуй та перезапусти web:
    docker compose -f ui/docker-compose.yml up -d --build web

Установка кореневого CA на iOS / iPadOS

  1. Перешли файл rootCA.pem на пристрій (AirDrop / email)
  2. Відкрий файл → з'явиться повідомлення "Profile downloaded"
  3. Settings → General → VPN & Device Management → "mkcert development CA" → Install (тричі підтвердити)
  4. Settings → General → About → Certificate Trust Settings → ввімкни перемикач навпроти "mkcert development CA"
  5. Відкрий https://homeServ2.local/ у Safari — повинно працювати без попереджень із зеленим замком
Один CA — багато пристроїв. Серт валідний для всіх перерахованих імен (homeServ2.local, IP, localhost). Кожен новий пристрій (телефон, планшет, інший комп) потребує однократної установки rootCA.pem.

Альтернативи

  • Let's Encrypt + DNS challenge — справжній серт, валідний на iPhone без установки CA. Потребує доменного імені (DuckDNS, FreeDNS) і налаштування certbot DNS-01.
  • Tailscale / Cloudflare Tunnel — приватний тунель з автоматичним валідним сертом. Дозволяє доступ і поза домашньою мережею.
  • HTTP без TLS — найпростіше, але браузер показує "Not Secure" і WebSocket має бути ws:// (не wss://).

Детальна інструкція з кодовими прикладами — у ui/frontend/ssl/README.md.

Мобільні пристрої

Система підтримує доступ з телефонів і планшетів через звичайний браузер (Safari, Chrome). Окрема нативна програма не потрібна.

Авто-вибір мобільного екрана

При першому завантаженні головної сторінки клієнтський JS викликає matchMedia('(max-width: 768px)'). Якщо результат істинний — система шукає у project.json екран зі screenType: "mobile" і найменшим screenNum для поточного deviceType і завантажує його. Якщо такого екрана немає (або файл відсутній) — fallback на PC-екран. Користувач може потім вручну переходити по кнопках навігації, але переходи між типами заблоковані (mobile↔mobile тільки).

Адаптивна верстка

Усі основні сторінки мають @media (max-width: 768px) блоки CSS:

  • Головна (/) — компактний хедер: лого до іконки, ховаються розділювачі, ім'я користувача, дата в годиннику; кнопка "☰ Меню" → "☰". Канвас використовує більше площі.
  • Адмін (/admin) — таби горизонтально скролляться, таблиці отримують min-width + горизонтальний скрол всередині .tab-panel, модалки — на повну ширину екрана.
  • Архіватор (/arch/, /arch/point.html) — фільтри переносяться, таблиця у .table-wrap зі скролом, графік стискається до 280px по висоті, контролі стають вертикальними.

Авторизація на мобільному

JWT в localStorage валідується при кожному завантаженні головної сторінки: декодується payload, перевіряється exp. Якщо токен прострочений — записи token, role, display_name, permissions очищуються, користувач показується як operator (не залогінений). Це запобігає ситуаціям, коли пристрій показує "залогінений як admin" із застарілими даними.

Розмір канваса для iPhone 13 / типового смартфона

Доступна площа на iPhone 13 (390×844 CSS px у портреті):

  • Мінус хедер 52px і футер 28px → 390×764
  • Мінус padding canvas-area (32px) → 390×732
  • Мінус відступ у _updateScale() (32px) → 358×700 — максимум без масштабування

Рекомендовані розміри для мобільних екранів: 360×640 (універсальний, fits iPhone SE+) або 360×700 (iPhone 13+ максимум).

Обмеження

  • Браузер не дає сторінці програмно піти в повний екран без жесту користувача. Ховання адресного рядку Safari доступне лише через "Add to Home Screen" (PWA-режим).
  • На iOS Safari requestFullscreen() не підтримується для не-відео елементів.
  • Без установки кореневого CA (див. TLS) браузер показує попередження про небезпечний сайт.

Потік даних

Розуміти як значення проходить від датчика до екрана корисно для діагностики і планування.

Шлях аналогового значення

  1. Симулятор або реальне обладнання публікує JSON у MQTT-топік {object}/{system}/{pointname}/{id} кожну секунду
  2. Core підписаний на # на брокері, отримує повідомлення → парсить → кладе в буфер (тред-сейф)
  3. Раз на 1с (system tick) Core читає буфер цілком, обробляє кожну точку:
    • Перевіряє топік — має співпадати з очікуваним для меті точки (захист від чужих)
    • Застосовує deadband — якщо |new − last| < deadband, пропускає
    • Класифікує якість (process_quality) — переходи стану
    • Записує в Redis hash point:NNN (один pipeline на весь батч)
    • Публікує ID у Redis Pub/Sub bus:data
    • Якщо стан змінився — додатково публікує подію у bus:event
  4. Backend має WebSocket з'єднання з кожним відкритим клієнтом. Підписаний на bus:data:
    • Збирає point_id за batch_interval=200мс
    • Один pipeline-запит до Redis за всіма зміненими точками
    • Шле батч у WS-фрейм: {"type":"update","data":[…]}
  5. Клієнт отримує батч у onmessage:
    • Мутує points[id] — Alpine реактивно перерендерить біндінги
    • Gauge використовує WeakMap-кеш по сигнатурі (значення + ліміти + кольори), щоб не перебудовувати арки 11 разів на render
    • Оновлюється lastUpdate у футері
  6. Паралельно Архіватор теж слухає bus:data і пише значення на диск згідно стратегії точки

Шлях heartbeat

  1. Кожен Python-сервіс у фоновому треді кожні 5 секунд робить SET heartbeat:<name> <timestamp> EX 25
  2. Контейнери без Python (redis, mosquitto, nginx, portainer) — infrabox-adm робить це за них через перевірку Docker API
  3. Core кожні 25 тіків (~25с) читає всі heartbeat:* ключі pipeline'ом
  4. Для кожного software-сокета з відповідним name: якщо TTL > 0 → value=1, quality=GOOD, інакше value=0, quality=ALARM
  5. Записує в point:NNN + публікує bus:data — далі стандартний шлях

Шлях selfDiag (метрики хосту)

  1. infrabox-selfdiagnostic змонтовано /proc та / хосту
  2. Через psutil читає cpu, memory, disk, network
  3. Кожну секунду публікує MQTT топік home/selfDiag/{pointname}/{id}
  4. Далі стандартний шлях через core

Управління — режими та елементи

Infrabox підтримує два режими управління підсистемами: автоматичний і ручний. Режим встановлюється на рівні системи (наприклад, reserv_power, electric…) і впливає на поведінку всіх контрольних точок, що входять до неї.

Режими управління

РежимОписПоведінка контрольної точки
Авто Core автоматично обчислює команди за SR-latch формулами (formula_on / formula_off) Команди видаються автоматично. Ручні команди ігноруються. Колір рамки — за станом якості фідбеку.
Ручний Оператор видає команди вручну через UI Автоматичні формули не застосовуються. Ручна команда → WARN → GOOD (після підтвердження). Колір рамки GOOD показує colorManual.

Елемент «Режим системи» (ctrl_opmode)

Відображає поточний режим підсистеми. Клік → діалог підтвердження зміни режиму. Рамка видима лише в автоматичному режимі (value = 1). Перемикання потребує права ctrl_signal або ролі admin.

Елемент «Управляючий сигнал» (ctrl_signal)

Прив'язується до контрольної точки типу control. Показує стан точки через колір рамки. Активний (клікабельний) лише в ручному режимі відповідної системи. Клік — ручна команда на інвертування поточного значення.

Елемент «Кнопка управління» (ctrl_btn)

Аналог ctrl_signal у вигляді кнопки з текстом та SVG-іконками. В автоматичному режимі затемнюється (opacity: 0.45) і не реагує на кліки. Колір тексту в авто-режимі задається окремим параметром colorInactiveText.

Права доступу: клік на будь-якому елементі управління без права ctrl_signal (і не маючи ролі admin) показує сповіщення про відмову в доступі — без зміни стану.

Управління — стани та кольори

Контрольна точка (type: control) має власний статус ctrl_status, який відображається кольором рамки елемента. Статус не залежить від якості самої точки — він відображає стан циклу управління.

Стани ctrl_status

СтанКолір (за замовч.)Значення
NODATA● темно-сірийПочатковий стан до першої оцінки (тільки при старті системи)
WARN● жовтийКоманда видана, очікується підтвердження від фідбек-параметра
GOOD● зеленийФідбек підтвердив команду. В ручному режимі показується колір colorManual.
ALARM● червонийТаймаут очікування фідбеку або фідбек-параметр у поганому стані (WARN/ALARM/NODATA/INIT). Відображається в обох режимах.

Кольори в ручному режимі

У ручному режимі WARN і ALARM завжди показують свій колір (попередження та аварія). Стан GOOD відображається кольором colorManual (за замовч. сірий #8b949e) — щоб оператор розрізняв ручне підтвердження від автоматичного.

Налаштування кольорів у конструкторі

ПараметрСтанЗа замовч.
colorManualGOOD у ручному режимі#8b949e
colorGoodGOOD в автоматичному режимі#3fb950
colorWarnWARN (очікування фідбеку)#f0ad4e
colorAlarmALARM (таймаут або проблема фідбеку)#f47067

Вплив якості фідбек-параметра

Якщо фідбек-параметр переходить у стан ALARM, WARN, NODATA або INIT — контрольна точка незалежно від режиму (авто або ручний) переходить у ALARM. Управління при цьому не блокується — оператор може видати нову команду, але бачить сигнал аварії.

Управління — потік команди

Ручна команда (ручний режим)

  1. Оператор клікає на елемент управління → підтверджує дію у діалозі
  2. UI надсилає POST /api/points/{id}/value з новим значенням (інверсія поточного)
  3. Backend одразу пише в Redis: point:{id} quality=WARN, встановлює ключ manual_cmd:{id} (TTL 30с), публікує bus:data
  4. UI отримує WS-оновлення і показує стан WARN (жовта рамка) — ще до обробки core
  5. На наступному такті (до 1с) Core читає manual_cmd:{id}, видає команду через MQTT на пристрій, встановлює ctrl_status=WARN
  6. Пристрій реагує → фідбек-параметр змінює значення → на наступному такті Core бачить збіг і встановлює ctrl_status=GOOD
  7. UI отримує GOOD — рамка показує colorManual (сірий)
Мінімальна тривалість WARN: один такт системи (за замовч. 1с). Якщо пристрій відповідає за 50мс — все одно WARN видно 1 такт, потім одразу GOOD.

Автоматична команда (авто режим)

  1. Core щотакту обчислює formula_on / formula_off (SR-latch)
  2. Якщо умова спрацювала і значення фідбеку ще не відповідає команді — видає MQTT-команду, встановлює ctrl_status=WARN
  3. Фідбек підтверджує → GOOD. Таймаут (за замовч. 10 тактів) → ALARM
  4. ALARM RECOVERY: якщо пристрій пізніше таки відповів — ALARM → GOOD автоматично

SR-latch логіка формул

Команди визначаються формулами у форматі $<point_id>:

УмоваДія
formula_on = true, formula_off = falseВидати команду ON (value = 1)
formula_on = false, formula_off = trueВидати команду OFF (value = 0)
Обидві = trueБезпечний стан: команда OFF
Обидві = falseУтримати поточний стан (hold)

Ключ manual_cmd у Redis

Механізм передачі команди з UI в Core:

  • Ключ manual_cmd:{point_id} — рядок із значенням команди (0 або 1)
  • TTL = 30 секунд (команда автоматично скасовується якщо Core не прочитав)
  • Core читає і видаляє ключ на початку GATE 1 (перевірка режиму) — до виконання формул
  • Після відправки MQTT-команди Core встановлює ctrl_status=WARN і запускає зворотний відлік тактів очікування фідбеку
